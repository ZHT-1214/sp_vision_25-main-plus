# 线程数据传输模型：内部设计与实现细节

本篇文档面向框架核心开发者，详细解析 `threads` 包中 `LatestBuffer` 和 `LatestChannel` 内部的并发设计取舍与实现原理。

如果您只是想了解如何在业务中使用它们，请优先阅读外层的 [README](../README.md)。

---

## 1. `LatestBuffer` 的极简与严苛

`LatestBuffer<T>` 专为“流水线式的单向流动”设计。它的底层实现极其精简，直接依赖标准的 `std::mutex` 和 `std::condition_variable`。

### 1.1 极致的调度开销
由于其语义明确定义为“单消费者”，所以在数据写入后，框架内部只会调用 **`notify_one()`**。这种模型下唤醒路径极其简短明确，不存在惊群效应，非常适合高频流水线（如相机取流到算法检测）上的极限性能传输。

### 1.2 为什么天生只适合 1 对 1 流水线？

**关于消费者（单收）：**
`LatestBuffer` 的核心动作语义是 **“取出即清空”**（`wait_pop` 会移动数据并置空内部槽位）。如果允许多个消费者线程同时等待获取，谁先被系统调度唤醒，谁就会独占这帧数据并将槽位再次置空。这会导致其他的消费者要么被无尽地阻塞，要么错位地读到下一帧数据，造成多条处理链路的时间戳严重脱节。

**关于发布者（单发）：**
虽然底层的 `mutex` 保证了多线程并发调用 `push()` 是绝对安全的，但由于这是 Latest-Only（覆盖旧值）模型，如果多个毫不相干的发布者并发往里 `push()` 数据，会发生极为惨烈地互相覆盖。唯一的那个消费者最终只能拿到被切碎、跳变的混乱片段。
因此， **尽管在并发语法上支持多发**，但在工程实践中，我们强烈建议将其严格作为**单发单收的私有流水线**来使用。

## 2. `LatestChannel` 的广播与轻量

`LatestChannel<T>` 专门用于“一发多收”的全局状态广播场景。为了追求极致的无锁读写性能，它在设计上做了两点极为重要的取舍：

### 2.1 强制使用 `shared_ptr<const T>` 实现零拷贝
由于订阅者数量不确定，如果在底层为每个订阅者复制一份完整的消息对象，当遇到图像帧 (`cv::Mat`) 或点云这类庞大的数据时，极高的拷贝开销将是系统不可承受的。

因此，设计上强制发布者提供智能指针，而订阅者拿到的必须是**只读引用** (`std::shared_ptr<const T>`)。
这一设计达成了两个目的：
1. **零拷贝通信**：无论有多少个活跃的订阅者，大对象本身在堆内存上永远只有一份。
2. **防数据竞争**：通过 `const` 约束，确保不会有某个“捣乱”的订阅者去修改共享数据而干扰其他人的正确性。

### 2.2 为什么不维护订阅者列表？
通道底层**不维护任何订阅者列表**（没有 `std::vector<Subscriber>`）。这带来了巨大的性能优势：
发布数据时，具备 **O(1) 的超低复杂度**。只需原子的更新全局 sequence 游标并执行一次 `m_seq.notify_all()`，无需加锁去遍历庞大的订阅者列表来执行用户态唤醒。

*(注意：`notify_all()` 仍会让挂起的底层系统线程被唤醒并参与调度。因此单通道也不应被大量“平时不消费”的休眠订阅者无节制地阻塞监听)*

### 2.3 为什么天生只适合 1 个发布者？
为了实现上述的 O(1) 发布，`Channel` 高度依赖单一的 `std::atomic<uint64_t>` 作为所有订阅者比对新旧的“版本游标”。如果放任多个发布者并发抢占写入：
1. **并发竞态**：多线程并发更新底层指针并执行 `fetch_add` 推进版本号，这二者的组合操作无法简单保持原子性。想象这样一个危险的执行时序：
   ```text
   1. 线程 A 刚刚将底层共享指针替换成了 data_A，还没来得及更新版本号。
   2. 线程 B 突然抢占 CPU，将共享指针覆盖成了 data_B。
   3. 线程 B 执行 fetch_add，将版本号推至 v101，并唤醒了订阅者。
   4. 订阅者醒来，读到了 v101 的 data_B。
   5. 线程 A 恢复执行，它也执行 fetch_add，将版本号推至 v102，并再次唤醒订阅者。
   6. 订阅者再次醒来，发现出现了新版本 v102，于是愉快地去读数据。但此时指针压根没更新，它读到的依然是刚才的 data_B！
   ```
   这种“版本号与数据内容撕裂”的绝望局面，如果想彻底解决，就必须在发布路径上引入极其笨重的互斥大锁，从而彻底毁掉 Channel 无锁发布的性能优势。
2. **时序跳变**：作为广播通道，如果多个源头都在无序写入，订阅者收到的时间线序列将发生极其混乱的跳变。

因此，为了保全极致轻量的无锁优势，我们严格将其**限制为单发布者的“一发多收”模型**。

## 3. 并发安全与死锁免疫论证

`threads` 组件在底层被精心设计为 **死锁免疫（Deadlock-free）** 的，只要是正常的接口调用，就绝不会在组件内部引发死锁僵局。

在操作系统理论中，构成死锁必须满足的一个关键条件是 **“占有并等待（Hold and Wait）”**，即线程持有一把锁的同时，再去等待另一把被别人锁住的锁。我们的架构从根本上杜绝了这种情况的发生：
* `LatestBuffer<T>::wait_pop()`：由于基于 `condition_variable`，在进入等待睡眠的瞬间，它会自动且干净地释放掉内部持有的 `mutex`。
* `LatestChannel<T>::wait_next()`：完全是由底层的无锁原语 `atomic::wait` 实现，在漫长的等待期间根本不需要持有 channel 的任何保护锁。
* `push()` 和 `publish()`：都只是在拷贝智能指针或转移数据的一瞬间短暂加锁，在函数退出前必定释放，绝对不涉及跨锁的嵌套函数调用。

因此，即使一个业务线程极其奔放地同时操作 10 个 buffer 和 channel，它也不会因为内部锁机制的牵连而陷入死锁。

### 🚨 真正的风险在于外部业务锁滥用
虽然通信组件内部坚不可摧，但它无法防止用户在外部业务代码中人为制造出“占有并等待”的窘境。典型的反面教材如下：
```cpp
// ----------------- 消费者线程 -----------------
std::lock_guard<std::mutex> lock(app_mutex); // 1. 业务层面占据全局互斥锁
auto msg = subscriber.wait_next();           // 2. 持有着锁进入长久睡眠，等待新消息...

// ----------------- 生产者线程 -----------------
std::lock_guard<std::mutex> lock(app_mutex); // 1. 试图获取全局锁（被消费者拿走了，卡死）
channel.publish(new_msg);                    // 2. 永远无法发布消息，消费者永远也等不到新消息
```
在这种错误写法下，整个系统瞬间陷入万劫不复的死锁死循环。

这就是为什么框架极其强调并警告的规则：**所有的跨线程取数据行为 (`wait_pop` / `wait_next`) 都必须裸跑。先拿到属于你的数据，如果该数据要求你修改跨线程的业务状态，再去去竞争你的业务互斥锁。**
